# ALEX AI architecture

```
Flutter app (frontend/)  <--HTTPS-->  FastAPI backend (backend/)  <-->  Groq, Fish Audio, Tavily, Newsdata, Serp, OpenWeather
        |
        +--MethodChannel "alex/native"-->  Kotlin layer (frontend/android_overrides/)  <-->  Android APIs
```
* **Flutter** owns all UI and the on-device command parser. It never holds third-party API keys. It stores only the backend address, an app token and an anonymous user id.
* **Kotlin** is one native layer inside the same app. Every capability is a `NativeService`; `CommandRegistry` routes channel methods to services. To add a feature: add a service file, add one line in `MainActivity.kt`, document it in `NATIVE_CHANNEL.md`.
* **FastAPI** holds all keys (`KeyPool` with automatic failover and manual switching), the LLM call, search/news/weather, text-to-speech, speech-to-text, per-user memory and personality.
* **Android folder**: `frontend/android/` is generated by `flutter create` in CI and is not committed; `tool/patch_android.py` copies the Kotlin files and adds permissions. This keeps Gradle/AGP/Kotlin versions matched to the pinned Flutter.

## Voice command flow
1. Text arrives (typed now; speech-to-text later).
2. `CommandParser` (Flutter) handles simple device commands instantly.
3. Otherwise `/chat` on the backend: the LLM answers or requests one whitelisted device action.
4. Flutter validates the action again (`CommandParser.fromAction`) and runs it through Kotlin.
5. The result is shown in the chat.
The LLM can never run shell commands: only `flashlight`, `volume`, `open_app` exist.
